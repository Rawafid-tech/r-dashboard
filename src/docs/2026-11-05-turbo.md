# Part 1 — Turbo

> Builds on `2026-10-23-wingezz.md` Part 1 (a carrier with no pickup to choose) and on
> `2026-10-30-speedaf.md` Part 1 (a connect form of secrets plus a switch).

**Status: deployed to staging (PR #74, 2026-11-05).** Checked on staging against Turbo's live API:
the seeded row is listed and enabled, 4,686 areas synced, Test Connection with a real key answers
`200` with no warnings, and a wrong client code answers `422`. Nothing was booked on staging.

**Known gap.** Of Turbo's 225 Cairo and Giza outskirts areas, only 37 are placed so far (15 Cairo,
22 Giza). The other 188 (compounds and landmarks such as دار مصر اكتوبر) are never matched: an order
there comes back unmatched, like any area the carrier doesn't list. No API change when that closes.

Turbo has its own API (platform `TURBO`). Merchants connect, book, track and cancel it the way they do
the other own-API carriers. There is **no new API shape**: every screen is driven by `fields` and
`capabilities` as before.

What is different, and what the screens must handle:

- **No admin form.** Turbo is seeded (migration V63) as Bosta is: code `turbo`. It is not in
  `GET /api/admin/carrier-platforms`, and an admin cannot add a second Turbo row. The admin list,
  enable switch, logo and region sync work on the row as on any other.
- **Two secret values, an optional phone and a switch to connect.**
  - The API key and the client code both come from Turbo.
  - `followupPhone` (TEXT, optional) is the merchant's mobile that Turbo's staff call about
    shipments. When it is not an Egyptian mobile, Test Connection answers the usual `422`.
  - `allowOpen` (BOOLEAN, default `false`) lets the customer open the parcel.
- **No pickup to choose.** Turbo collects from the address it holds for the account, as Wingezz does.
- **Deliveries only.** `capabilities.returns` and `exchanges` are `false`.
- **No cancel or print through Rawafid.** `capabilities` is `cancel: false`, `labels: false`,
  `tracking: true` and `refunds: false`. Turbo's own cancel refuses a parcel it hasn't collected yet,
  and its delete may only archive the parcel. Until that is settled, a cancel answers the usual
  `422 carrier.cancel.notSupported`, and the merchant cancels with Turbo directly. Hide the cancel
  button as for any carrier with `cancel: false`.
- **Tracking is polled.** Turbo pushes nothing.
- **Areas.** Turbo's list of the Cairo and Giza outskirts (October, Zayed, the New Capital…) is
  shared out between the two governorates area by area. An area Turbo doesn't cover is never matched.
  Nothing changes on screen: `address.method` / `district.method` as before.

## 1. Merchant screens

**Connect form.** `GET /api/carriers` lists Turbo with four `fields`:

```json
{ "code": "turbo", "fields": [
    { "key": "apiKey",        "kind": "SECRET",  "required": true,  "label": "API key (from Turbo)" },
    { "key": "clientCode",    "kind": "SECRET",  "required": true,
      "label": "Client code (the number Turbo gave your account)" },
    { "key": "followupPhone", "kind": "TEXT",    "required": false,
      "label": "Follow-up mobile Turbo calls about your shipments (optional)" },
    { "key": "allowOpen",     "kind": "BOOLEAN", "required": false, "defaultValue": false,
      "label": "Allow the customer to open the parcel" } ],
  "capabilities": { "labels": false, "cancel": false, "tracking": true, "returns": false,
                    "exchanges": false, "refunds": false } }
```

The two secrets travel in `credentials`; `followupPhone` and `allowOpen` travel in `options`.

**Test Connection** (`POST /api/carriers/turbo/test`) checks the key and client code with Turbo and
books nothing. A wrong one of either is the usual `422`. `pickupLocations` is empty and there are no
`warnings`.
